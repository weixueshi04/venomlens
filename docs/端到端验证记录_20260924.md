## 3. 关键前置：`adb reverse` 为什么会反复失效

这是本次最耗时的坑，根因与相机、网络都无关：

- **现象**：`adb -s daf22ef5 reverse tcp:8200 tcp:8200` 执行成功，但下一个命令再看 `reverse --list` 就空了，App 因此必然报「网络连接失败，请检查网络」。
- **根因**：**每条前台 shell 命令结束时，它自己拉起的 adb daemon 会随命令环境一起被回收**，转发表（存在 daemon 内）随之丢失。反证：某次命令结束后 `tasklist /FI "IMAGENAME eq adb.exe"` 返回「没有运行的任务」。
- **修复**：把「维持 reverse」放进**常驻后台任务**（`tools/reverse_watchdog.sh`）——只在缺失时补建，并用 1 秒一次的心跳把 daemon 钉住。之后跨 5 次前台 adb 调用 reverse 不丢。
- **判定隧道是否真的通的方法**（推荐固化为验收动作）：
  ```bash
  adb -s daf22ef5 shell 'curl -s -m 6 -o /dev/null -w "%{http_code}" http://127.0.0.1:8200/healthz'
  # 期望 200；对照组打一个必然不通的端口应返回 curl_exit=7
  ```
  设备侧 `curl`/`nc`/`netcat` 均存在（`/system/bin/`）。

> 顺带提醒：手机上同时存在 `emulator-5556`（模拟器，状态会 offline/online 抖动），所有 adb 命令务必带 `-s daf22ef5`。

## 4. 修复：上游 `1008 "No boxes"` 被错报为服务故障

### 4.1 定位过程（全部有原始数据支撑，非推测）

1. 首次跑通时界面报的是「**识别服务暂不可用**」——与「网络连接失败」是**两个不同的错误**，说明请求已抵达代理，是代理调用上游失败。
2. 查账本 `recognitions` 表，拿到该次记录的**代理返回体原文**：
   ```json
   {"requestId":"94d7c65f-...","resultSource":"live",
    "error":{"code":"UPSTREAM_ERROR","message":"模型返回业务错误"}}
   ```
3. 该 message 字符串在代码中唯一对应 `inference/provider.py` 的兜底分支
   `if code != 1000: raise ServiceError("UPSTREAM_ERROR", "模型返回业务错误")`。
4. 用 `tools/probe_upstream.py` 直连上游复现，排除网络与密钥问题：
   ```
   HTTP status = 200
   raw body    = [1000,"HH-R_20260924_02452532520_1"]     # 上传完全正常，返回任务 ID
   ```
5. 再用 `tools/probe_refresh.py` 对同一 taskId 查询（连续两次结果一致）：
   ```
   raw body = [1008,"No boxes"]
   ```
   → **1008 未在 `parse()` 中被处理**，掉进兜底分支被当成故障。语义上它是「画面中没有检测框」，属正常返回。

### 4.2 修法与依据

`contracts/recognition-contract.md` 第 49 行本就写死了口径：

> 供应商 `[1010,"No animals"]` **以及空检测结果**目前映射为 `uncertain`；即使使用 `class=R`，
> 未识别到爬行动物也不能证明蛇不存在。`no_snake` 暂仅用于模拟客户端状态。

因此正确映射是 **1008 → `uncertain`**（**不是** `no_snake`——单张画面没拍到蛇，不构成「现场没有蛇」的结论）。

改动：
- `inference/provider.py`：`if code in {1008, 1010}` + 注释留痕（含实测时间与原始响应）。
- `inference/tests/test_provider.py`：`test_no_animals_and_empty_results_are_not_safety_claims` 的用例集合加入 `[1008,"No boxes"]`。
- 结果：provider 测试 **21 项全绿**。

### 4.3 一个被排除的疑似诱因（记录以免后人误改）

PC 环境存在 `HTTPS_PROXY=127.0.0.1:49496`，而 `provider.py` 建 httpx 客户端时写死 `trust_env=False`，
看上去像「绕过代理导致连不上上游」。**实测排除**：`curl --noproxy '*' https://ai.open.hhodata.com/api/v2/dongniao`
同样可达（405 = 方法不允许，属正常响应）。**直连可用，`trust_env` 不是元凶，请勿改动。**

## 7. 两个必须注意的工程事实

1. **仓库里有两棵 inference 树**：`E:/insta/inference/` 是**旧副本**（8 个文件全部与活的版本不同），
   真正在跑的是 `venomlens_怕草绳/inference/`（账本写在 `venomlens_怕草绳/.runtime/` 可证）。**不要改错树。**
2. **代理当前跑在某个会话的后台任务里**，会话结束会随之停止。
   手动重启命令：`cd venomlens_怕草绳 && python start_proxy.py 8200`
   （`start_proxy.py` 默认端口是 8765，**必须显式传 8200** 才能对上 App 的 baseUrl）。
