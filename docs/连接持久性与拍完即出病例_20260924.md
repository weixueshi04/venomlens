## 二、断连根因：真机 logcat 实证

**这不是推测，是设备上抓到的原话。** 复现方式：App 已连相机（Wi-Fi，Insta360 X5 / SN IAHEA2503JFTVP），切到别的软件约 40 秒再切回。

```
02:54:26.200 I/SmartPower: com.insta360.kmpsdk.demo/10348(27434): idle->background(40206ms) adj=200
                ↑ 已经在后台 40.2 秒
02:54:26.210 E/OneCameraSocketIO: inPacketDurationSinceLatestMs 43817 233240551
02:54:26.210 E/OneCameraSocketIO: mOnErrorCallback ERR_TIMEOUT
                ↑ 距上次收到相机包已 43.8 秒 → SDK 判心跳超时
02:54:26.212 I/[SocketManagerCore] C++ 层错误回调: errorCode=-19
02:54:26.225 E/OneDriverImpl: reconnectIfNeed = false, kWhatError -19
                ↑ SDK 自己决定**不重连**
02:54:26.248 I/UnifiedTransport: [connection][onCameraError] error=-19
02:54:26.290 I/DeviceCoreImpl: start handle Disconnected(connectType=WIFI,
                throwable=NativeException: Forced to disconnect from camera, error=-19)
02:54:26.303 W/ConnectionViewModel$disconnectListener: camera disconnected (listener)
                ↑ 我们收到事件后无条件走「彻底收工」
02:54:26.333 D/CameraSessionForegroundService: CameraSessionForegroundService onDestroy
                ↑ 连保活通知都被撤了
```

**结论链条：**

1. App 进后台 → 相机 socket 静默 40 余秒；
2. SDK 按静默时长判 `ERR_TIMEOUT`（error=-19）；
3. **SDK 明确 `reconnectIfNeed = false`，链路不会自愈**；
4. 我们的 `disconnectListener` 收到事件后无条件执行「彻底收工」：release 相机、解绑进程网络、发断连信号（各页弹窗并踢回连接页）、**停掉前台服务**；
5. 全程**没有任何自动重连**——只能人工回去点「Wi-Fi连接」。

**关键对比（同一份日志里）**：用户在 02:54:31.090 手动点连接后，`.143` 就 `onCameraConnect` 了——
**约 50ms 就连上**。也就是说链路完全健康，重连成本极低，缺的只是「谁去按那一下」。

## 三、改动清单

### 3.1 连接持久性（`ui/connection/ConnectionViewModel.kt`）

| 改动 | 说明 |
|---|---|
| `handleDisconnected` 分岔 | 按「谁掐断的」分流：用户主动 → `finishDisconnected`（原逻辑）；链路被被动掐断 → `handleTransientDisconnect` |
| `handleTransientDisconnect` | 轻量拆除：释放相机对象，但**保留**进程网络绑定与前台服务；**不发**断连信号。因此不会弹「相机已断开」对话框，也不会把用户从紧急流程踢回连接页 |
| `scheduleAutoReconnect` | 有界退避 `0 / 0.8 / 2 / 5 秒`，最多 4 次；用尽了才真正收工 |
| `attemptReconnectOnce` | **重放**用户当初那条连接入口（`reconnectInvoker`），并以 `ConnectState` 终态判成败；单次上限 8 秒 |
| `releaseStaleDeviceBeforeReconnect` | 竞态修复：陈旧设备的 `release()` 会在 `connect()` 之后执行时把新会话又拆掉，所以改成寄存在 `deviceAwaitingRelease`，重连**前**按序释放 |
| `startSessionKeepAlive` | 连接期间每 10 秒发一次极轻的取电池往返，把 SDK 的静默窗口从 40s 量级压到 10s 量级 |
| `onAppForegrounded` | 由 `MainActivity.onResume` 调用：回前台时若仍有「待自愈」标记，立刻再补一刀重连 |

### 3.2 其它

- `MainActivity.onResume` → `ConnectionViewModel.onAppForegrounded()`；
- `AndroidManifest.xml`：`MainActivity` 加 `android:launchMode="singleTop"`，避免任何「再起一个实例」的入口把旧实例连同它的 ViewModel 一起销毁（ViewModel 一走 `onCleared` 就会 release 相机）；
- 新增字符串 `camera_reconnecting` / `reconnecting` / `camera_reconnect_failed`（中英双份）。

### 3.3 网络优先识别

- 新增 `recognition/RecognitionProxyHealth.kt`：识别前短超时（1.5s）探测代理 `/healthz`；
- `EmergencyFlowViewModel.createAdapter()` → `resolveAdapter()`：
  - **删掉**「配置构造失败就悄悄换成 fixture」的静默降级；
  - 探测通过 → 真实识别；不通过 / 未配置 / 配置不合法 → 才落本地 fixture，**并把原因写进界面**（`emergency_flow_stage_recognizing_local` + `emergency_flow_fallback_proxy_unreachable` 带出 baseUrl），来源标注仍是 MOCK 红标，不伪装；
- 语义决策：**拿到任何 HTTP 响应（含 4xx/5xx）都算「代理在」**。5xx 说明代理自己有毛病，那种情况必须让真实请求失败并如实报错，而不是悄悄换成本地数据集糊过去。这一条是被单测抓出来的——我第一版写成了 `code in 200..299`，测试直接判 FAILED。

### 3.4 咬伤情况三态 + 拍完即出病例

- `CaseRecord.kt`：`CaseDraft.bitten: Boolean` → `biteStatus: BiteStatus{UNKNOWN, BITTEN, NOT_BITTEN}`；JSON 升到 v2 并兼容读 v1；`cardText()` 对 UNKNOWN 输出「咬伤情况：未提供（未填写不代表未被咬，请保持距离）」；v2 不再写 `bitten` 字段（留着会让「未知」在旧读取方眼里又变成 false）；
- `CaseRecordActivity`：
  - **修掉隐患**：`restoreDraft()` 原先用 `getBooleanExtra(EXTRA_BITTEN, false)`，意图缺失时会把「用户没说」渲染成「未被咬（用户填写）」这句安全声明。改为 `EXTRA_BITE_STATUS` + 缺失落 `UNKNOWN`；
  - 只有明确「被咬」才展开咬伤细节字段；
  - 新增「演示填充」：只预填**照片推不出来**的可选字段（部位/症状/年龄/血型/联系人…），且卡片上必挂「【演示数据】」横幅；默认关，开关在「Mock识别(开发)」页；
- 自动出卡：`renderSuccess` 拿到终态（含 uncertain / 无候选）后 `maybeOpenCaseAutomatically()`，一轮链路只自动打开一次；咬伤情况恒传 `UNKNOWN`——照片和识别链路都推不出「有没有被咬」，自动打开更不能替用户认领一个安全结论。

### 4.1 真机验证 A：连接持久性 —— 通过

设备 `daf22ef5`（Xiaomi 2210132C）+ Insta360 X5（SN `IAHEA2503JFTVP`），产物目录 `logs/persist-082849/`。

操作：App 已连相机 → 按 HOME 切走 **70 秒** → `am start` 拉回。

| 判据 | 实测 |
|---|---|
| 切走前界面连接态 | `已连接（WIFI）` |
| 后台期间前台服务是否存活 | **1**（`dumpsys activity services … isForeground=true`） |
| **后台期间的保活握手** | 16 次 `fetchOptions ==>[BATTERY_INFO]` 往返，**16 次全部 `responseCode:200`**，带回真实电量 `battery_level=15`（过程中升到 16）。其中 **9 次落在后台窗口内**（08:29:11 / :23 / :33 / :41 / :43 / :53、08:30:03 / :12 / :13） |
| 回到前台后连接态 | `已连接（WIFI） · Insta360 X5` |
| `ERR_TIMEOUT` / `errorCode=-19` / `reconnectIfNeed` | **0 次**（grep 全库无匹配） |
| `camera disconnected (listener)`（硬断连弹窗信号） | **0 次** |
| `CameraSessionForegroundService onDestroy` | **0 次** |

**结论**：后台 70 秒期间链路全程存活，没有发生断连，因此也无需触发自动重连。这比以前「40 秒就判死」是质变——
10 秒保活心跳把 SDK 的静默窗口压到了阈值以下，**问题在源头被消除了，而不是靠事后补救**。

一个必须说明的观察（**非本轮引入**）：

- `W/OneCameraSocketIO: not write while connection closed` 出现 82 次，**严格 1.50 秒等间隔**。
  我们自己的循环周期是 1s（健康检查）与 10s（保活），都对不上 1.50s，因此这是 **SDK 自带的 socket 心跳**行为；
  且它在 App 还在前台（08:29:00，界面显示已连接）时就一直如此。同期所有真实请求都拿到 `responseCode:200`，
  说明它不影响命令通路。属于厂商 SDK 内部噪音，**未处理，也建议不改**（改它等于改供应商行为）。

### 4.3 本轮修掉的两个**工具链** bug（差点让结论跑偏）

1. **`parse_ui.py` 拿到 POSIX 路径直接 FileNotFoundError 且被 `2>/dev/null` 吞掉** →
   `ui_text` 返回空串 → 脚本打印「阶段0 status_text = ''」并断言「尚未连接相机」。
   **相机其实一直连着**。修法：`wpath()` 用 `cygpath -w` 转 Windows 路径 + 新增 `assert_parsed()` 护栏
   （解析节点数 < 3 立即 exit 4，并回显被吞的错误）。
2. **前置检查查错了控件 id**：连接态在「连接」页叫 `status_text`，在「一拍知蛇」页叫 `connection_status_text`。
   只查前者 → 把「其实连着」判成「未连接」（脚本 exit 3）。修法：两个 id 依次取，都取不到才判失败。

另外两处顺手加固：
- `adb reverse --list | tail -1` 偶发返回空（不代表隧道没建）→ 改为以**设备侧 `curl` 实测** `http_code=200` 为准；
- `adb pull` 的**宿主**目的路径同样是 POSIX，会报 `cannot create file/directory` → 一并走 `wpath()`。

## 五、本轮明确**没有**验证到的 / 残余风险

1. **自动重连路径本身没有被这次真机跑「真的触发」过**。A 跑通是因为保活心跳让断连根本没发生——
   这是好结果，但也意味着 `scheduleAutoReconnect` / `attemptReconnectOnce` /
   `releaseStaleDeviceBeforeReconnect` 这段代码**在真机上仍然只有推理与单测支撑**。
   要真正验收它，需要一个能强制断连的用例（例如测试中把相机 Wi-Fi 关掉 30 秒再恢复）。
2. **Activity 被系统回收**这条路径没处理：`MainActivity` 若在后台被销毁，`ConnectionViewModel.onCleared()`
   仍会 release 相机，用户回来会看到「未连接」。只做了降低概率（`singleTop`），没做进程级会话寄存。
3. **`configChanges`（暗色模式/语言切换）会重建 Activity**，同样会走 `onCleared`。没动，因为改它是未经验证的行为变更。
4. **保活心跳只验证了「有效」，没验证「代价」**：每 10 秒一次往返对相机电量的影响没有量化。
   实测期间相机电量 13%→20%（且 `power_type=ADAPTER_`，疑似接着电源），不足以得出结论。
5. **识别准确率没有验证**：本轮演示环境未拍到蛇，拿到的是 `1008 No boxes`（映射为「无法判断」）。
   「真的拍到蛇能不能给出正确候选」仍未被端到端验证过。
6. **单设备假设**：`tools/reverse_watchdog.sh` 只维护 `daf22ef5` 一台；多设备时需显式传 `-s`。

### 6.2 装回真机：MIUI 把安装确认弹窗「吞掉」了

清干净之后要把 App 装回设备，结果 `adb install` 一路 `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`，
换了五条通路 + 压平两个 settings 键，全部同样失败：

```
adb install -r / --no-streaming / --user 0 / -t / -i com.miui.packageinstaller / -i com.android.vending
settings put global adb_install_need_confirm 0     → 已是 0
settings put secure adb_install_need_confirm 0     → 已置 0
pm install -r /data/local/tmp/snakesnap.apk        → 同样失败
```

`adb_install_need_confirm` 明明是 0，却仍在报「Install canceled by user」——说明拦截不在这个开关上。
转去看 logcat，一次就看清了（**这类问题不要靠猜设置项，直接抓 logcat**）：

```
I TopActivityMonitor: TopActivityChangeEvent(prev=
    ComponentInfo{com.miui.securitycenter/com.miui.permcenter.install.AdbInstallActivity},
    current=ComponentInfo{com.miui.home/com.miui.home.launcher.Launcher}, appChanged=true)
E PKMSImpl: MIUILOG- assertCallerAndPackage: uid=2000, installerPkg=null,
    packageName: com.insta360.kmpsdk.demo, msg=Install canceled by user
D PackageInstallerSession: Marking session 1762149847 as failed:
    INSTALL_FAILED_USER_RESTRICTED: Install canceled by user
```

MIUI 的机制是：`adb install` 会拉起一个**需要真人点确认**的 `AdbInstallActivity`
（在 `com.miui.securitycenter` 里），确认了才继续。而它这次出现后 **0.1 秒就被关掉**了。

根因是**通知栏正开着并占着焦点**：

```
mCurrentFocus=Window{cbaefee u0 NotificationShade}
```

下拉通知栏遮住屏幕时，MIUI 的确认弹窗一露头就失去焦点、立刻结束 → 变成「cancelled by user」。
把通知栏收掉再装：

```
adb shell input keyevent 4      # BACK 收起通知栏
adb shell input keyevent 3      # HOME 回桌面
adb -s daf22ef5 install -r app-debug.apk
    Performing Streamed Install
    Success
```

**这条坑的普适形态**：MIUI/部分国产 ROM 的 adb 安装会弹一个真人确认框；
只要屏幕被通知栏/锁屏/另一个 Activity 压住，这个框就会被瞬间取消，而报错文案（"Install canceled by user"）
看起来像是「用户拒绝」，很容易把人引去查 `adb_install_need_confirm` 这类开关——
**真实原因在窗口焦点，不在安全设置**。判定方法就是 `dumpsys window | grep mCurrentFocus` 看焦点在谁身上。
